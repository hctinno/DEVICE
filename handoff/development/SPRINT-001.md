# 첫 병렬 개발 묶음 — DEV-SPRINT-001

2026-10-23, Asia/Seoul. 총괄이 기존 승인 범위의 다음 작은 구현을 개발1~3에 배정한다. 개발4의 [DEV4-UI-001](DEV4-UI-001.md)은 그대로 진행한다. 사용자에게 개발 단위마다 별도 시작 지시를 요구하지 않는다.

## 목표와 공통 경계

기존 [접수 기반](../../docs/fcc/active_intake_usage.md)과 [가상 RF 환경](../../docs/fcc/virtual_lab_usage.md)에 문서 해석, 작업자 실행, 가상 세션 복구를 각각 추가한다. 각 단위를 따로 검증한 뒤 총괄이 한 업무 흐름으로 통합한다. 실제 모델 공급자·자격증명·비용 설정과 실장비 운전은 이번 단위의 시작 조건이 아니다.

각 담당은 자신의 독립 clone·전용 브랜치에서만 작업한다. 총괄이 전달한 시작 SHA를 확인하고 작업 트리가 깨끗하면 fast-forward로 인수한다. 변경·분기 이력이 있으면 reset이나 강제 덮어쓰기 없이 총괄에게 알린다. 수집 공유 폴더와 다른 개발 clone에는 쓰지 않는다.

공통 `schema.sql`, `store.py`, `active_intake.py`, `intake_analysis.py`, `intake_jobs.py`, `virtual_lab.py`, `virtual_scenarios.py`, `__main__.py`, `requirements.txt` 및 루트 계획/인계 문서는 이번 병렬 단위에서 수정하지 않는다. 새 파일 이름은 다른 담당 소유 범위와 충돌하지 않게 유지한다. 공통 수정이 필요하면 필요한 필드·호출·검증 이유를 총괄에게 제시한다. 세부 설계/계획 문서는 자기 작업 ID를 포함한 새 파일로 작성할 수 있다.

## DEV1-DOC-001 — 원본과 페이지 근거를 보존하는 추출

입력은 제공된 파일 바이트와 파일 이름이며 첫 대상은 UTF-8 텍스트와 텍스트 PDF다. 기존 접수의 원본 SHA-256과 연결 가능한 독립 추출 결과를 만든다. 실제 고객/제한 원문을 공개 테스트에 넣지 않고 직접 생성한 합성 PDF를 사용한다.

- 출력 계약에는 형식 버전, 원본 SHA-256, 파서 식별/버전, 전체 처리 상태, 페이지별 번호·추출 텍스트·추출 텍스트 hash를 포함한다. PDF 인용은 추출된 텍스트를 가리키며 원본 PDF 바이트 자체와 같은 것으로 표현하지 않는다.
- 페이지 경계·페이지 안의 줄 위치를 보존해 후속 분석의 근거를 찾을 수 있게 한다. 기존 `line_start/line_end` 분석 계약을 몰래 바꾸거나 PDF 내용을 원본 UTF-8 텍스트인 것처럼 제공하지 않는다. 기존 접수와의 통합 지점은 사용법에 제안한다.
- 암호화·손상·지원하지 않는 형식·스캔 PDF·텍스트 없는 페이지·크기/페이지/출력 한도를 구별한다. 부분 처리나 잘림을 완전 성공으로 표시하지 않는다. OCR, Office 자동화, 매크로 실행, 외부 전송은 수행하지 않는다.
- 추가 파서 의존성이 필요하면 별도 `requirements-extract.txt`에 기록하고 자기 가상환경에만 설치한다. 기존 공통 의존성은 총괄이 통합 시 검토한다.
- 문서 본문의 명령문은 데이터로 보존하며 코드·셸·운영 위임으로 실행하지 않는다.

수용 검사: 다중 페이지 인용 위치·같은 원본의 재현성·원본 hash·암호/손상/빈/스캔/제한 초과·한국어 텍스트를 확인한다. 표의 의미 해석이나 OCR 정확도를 구현한 것으로 주장하지 않는다. 테스트와 작은 명령행 예제를 제공하고 통합이 필요한 사항을 별도로 보고한다.

## DEV2-WORKER-001 — 제한된 접수 작업 실행기

기존 `claim_job`, `complete_job`, `fail_job`을 호출하는 독립 실행기를 만든다. 첫 버전은 현재 텍스트 분석 계약을 사용하므로 개발1의 결과나 새 UI를 기다리지 않는다.

- 한 번 실행 또는 명시적인 작업 수/실행 시간 한도 안에서 작업을 인수하고, 분석 제공자 호출 후 결과를 기존 검증기로 완료 처리한다. 제공자 미설정·잘못된 설정은 작업을 소모하기 전에 명시한다.
- 제공자 경계는 작업 문맥을 받아 분석 응답을 반환하는 어댑터로 두고, 실제 모델 API 없이 합성 제공자로 재현 가능하게 검증한다. 합성 제공자는 합성 접수에만 사용하며 실제 모델이 판단한 것으로 기록하지 않는다.
- 만료된 임대, 보완으로 바뀐 revision, 잘못된 응답, 제공자 실패·시간 초과를 성공으로 기록하지 않는다. 현재 임대에 대한 실패 처리와 임대 소유권 상실을 구별하고 기존 재시도 제한을 우회하지 않는다.
- 작업자 종료/재시작 뒤 기존 DB에서 다시 인수할 수 있게 한다. 중복 실행·중복 완료와 둘 이상의 작업자가 같은 작업을 가져가는 상황을 검증한다. 무한 재시도나 자동 데몬 설치는 하지 않는다.
- 문서 본문에서 도구 실행·권한 부여·명령어를 받아 실행하지 않는다. 비밀/자격증명을 로그에 남기지 않는다. 실제 모델 공급자 SDK·외부 API 호출·RF 명령은 이번 범위에 없다.
- 독립 진입점 `python -m labflow.intake_worker`를 제공할 수 있다. 공통 CLI와 DB 스키마는 유지한다. 시간 제한을 실제로 강제하지 못하는 제공자 형태는 지원 범위로 선언하지 않는다.

수용 검사: 정상 완료·작업 없음·설정 오류·제공자 실패·잘못된 근거·시간 초과·임대 만료·자료 보완·재시작·경쟁 인수·재시도 한도를 검증한다. 실제 모델 정확도와 상시 운영 완료는 별도 후속 검증이다.

공통 계약 보완: 개발2의 검토에서 합성 작업자의 사전 검사와 무필터 claim 사이의 경쟁 가능성이 확인됐다. 총괄이 `claim_job(..., synthetic_only=True)`를 추가했다. 합성 작업자는 이 원자적 필터를 사용하며, 실제 작업을 먼저 인수한 뒤 `fail_job`으로 반납하는 우회는 사용하지 않는다. 해당 옵션이 없는 구버전에서는 claim 전에 설정/호환 오류로 중단한다. 기본값 `False`는 기존 동작이다. 공통 모듈과 전용 회귀 검사는 총괄이 수정했고 개발2는 전달된 커밋을 인수한다. 전용 검사 7개와 전체 unittest 114개를 통과했다. 이 검증은 공통 인수 계약에 대한 것으로 개발2 작업자 전체의 완료를 뜻하지 않는다.

## DEV3-SESSION-001 — 가상 세션 영속화와 재개

기존 `VirtualLab`을 감싸 가상 시험 상태를 파일에 저장하고 새 프로세스에서 재개하는 단위를 만든다. 코드 실행 객체를 복원하는 pickle 등은 사용하지 않는다. 기존 가상 명령 의미와 여섯 시나리오를 변경하지 않는다.

- 버전 있는 JSON 기반 세션/이벤트로 초기 seed·설정과 순서 있는 입력을 보존한다. 재생 방식 또는 검증 가능한 명시적 상태 방식 중 적합한 것을 선택하고 이유를 기록한다.
- 허용된 가상 동작만 실행하고 요청 ID와 내용을 연결한다. 같은 ID/같은 내용의 재전송은 중복 동작 없이 기존 결과를 반환하며, 같은 ID/다른 내용은 거절한다.
- 재시작 전후 측정 ID, setup revision, 가상 tick, 완료된 관측값과 난수 재현성을 유지한다. 측정 진행 중 종료·중단 뒤 재개에서도 이전 결과를 새 측정처럼 표시하지 않는다.
- 파일 기록 중 실패·잘림·내용 변조·지원하지 않는 버전은 원본을 보존하고 명시적으로 실패한다. 초기 단위는 단일 작성자를 대상으로 하고 동시 작성은 손상 없이 거절하거나 직렬화해야 한다.
- 시나리오 작성자의 고장 주입/기대값과 운영자·AI가 읽는 관측을 분리한다. 관측용 반환값에 숨은 정답·고장 원인을 포함하지 않는다. 모든 결과는 합성으로 표시한다.
- 실제 DUT·계측기·네트워크·모델 API를 사용하지 않는다. 저장소 경로는 자기 clone의 비공개 작업 공간으로 제한한다.

수용 검사: 실행 중 저장→새 인스턴스/프로세스 재개→동일 관측, 완료 결과 중복 조회, 중복 요청, 충돌 요청, 손상/잘림/버전 불일치, 단일 작성자 보장과 고장 정보 분리를 확인한다. 기존 가상 시험 검사도 회귀 확인한다. 실장비 복구와 동일하다고 주장하지 않는다.

## 보고와 통합

각 담당은 작업을 실제 인수한 뒤 총괄에게 한 번 ACK하고 구현을 진행한다. 이미 승인된 범위의 통상적인 구현 선택 때문에 사용자에게 시작 승인을 반복 요청하지 않는다. 새 외부 비용·실장비 동작·제품 동작 범위 변경이 필요하면 총괄에게 구체적인 선택지를 전달한다.

문서 수정 후 `python scripts/check_artifacts.py` 및 새 문서의 UTF-8/로컬 링크를 검사한다. 기능 검사·정적 검사·가상 검증의 실제 결과를 나눠 적고 미실행 검사를 통과로 쓰지 않는다. 자기 브랜치에 커밋·푸시하고 총괄에게 SHA, 변경 파일, 실행법, 검사 결과, 남은 통합 사항을 보고한다. 총괄은 산출물별 검토와 공통 회귀 검사를 거쳐 개발 통합 브랜치에 반영한다.
