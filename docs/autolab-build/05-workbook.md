# 직원 작업 절차·배정·인수 양식

[시작 안내](../../AUTOLAB-BUILD-GUIDE.md) · [전체 구성](00-overview.md) · [작업 CSV](work-items.csv)

## A. 새 직원이 처음 할 일

1. 전체 구성과 맡은 챕터를 읽고 **본인이 수행할 작업 ID와 검토자**를 개발총괄에게 배정받는다. 아래 역할은 직무이며 직원 수를 뜻하지 않는다.
2. 현재 코드·자료·현장 상태와 해당 작업의 산출물을 대조한다. 이미 있으면 재사용하고 검증 증거를 인수한다. 다른 PC의 작업을 초기화하지 않는다.
3. 입력 자료·선행 작업·미확정 값을 확인한다. 막힌 이유는 “자료 없음” 대신 문서/자산/필드·필요 이유·담당·영향 작업으로 기록한다.
4. 작업카드를 만들고 산출물과 검증 방법을 먼저 적는다. 현장 운전은 기존 위임·절차·실행 조건을 확인한 범위에서만 수행한다.
5. 코드/도면/규칙/보고서와 검증 결과를 함께 제출한다. 실패·미검증·미지원도 기록한다.
6. 검토자가 증거를 보고 완료 상태를 결정하고 다음 담당자가 같은 버전을 인수한다.

## C. 작업 목록 운영

[work-items.csv](work-items.csv)는 초기 작업 분해표다. 모든 상태는 `미대조`로 시작한다. 이는 다른 PC의 기존 작업이 미착수라는 뜻이 아니다. B00에서 실제 상태를 대조한 뒤 `미착수 / 진행 / 검토 / 완료 / 차단 / 비적용`으로 기록한다. 완료에는 증거 경로가 필요하며 비적용에는 근거와 검토자가 필요하다.

열: 작업 ID·챕터·마일스톤·작업·담당 역할·시작 의존성·필수 산출물·완료 기준·요구사항 ID·상태·담당자·검토자·증거·개발 인일·현장 인일·외부 대기일. 의존성은 **착수에 필요한 계약/입력**을 뜻한다. 반복 개발은 가능하지만 게이트에는 관련 산출물의 최종 검토가 필요하다. 기간은 초기 값이 없으며 숫자를 임의로 채우지 않는다.

처음 작업 배정:

| 순서 | 병행 작업 | 합류 지점 |
|---|---|---|
| 1 | B00 현황 대조 → B01 실제 첫 조합·범위 결정 | G0 준비 |
| 2 | C1-01~04 근거/방법, C2-01~03 자산/제어, C3-01~04 접수/상태, C4-01~03 데이터/보고 | 각 계약 교차 검토 |
| 3 | C2-04 실제 제어 → C3-05 실제 업무 연결 → C4-04 비교·장애 검증 | G1 / M1 |
| 4 | C1-05 방법 확대, C2-05 RF/방사, C3-06 셋업/자원, C4-05 보고 확대; 해당 AC 셋업은 C2-06에서 우선 | G2 / M2 |
| 5 | C4-06 운영 인수; C1-06·C2-06으로 FCC 분야 확장, C2-07로 물리 병목 개선 | G3와 분야별 G4 |

M1에는 C1-01~04, C2-01~04, C3-01~05, C4-01~04의 필요한 최소 기능이 들어간다. C2-06은 AC와 SAR 등의 하위 작업으로 쪼개 각각 독립 검증한다. AC가 M2에 적용되면 SAR 완료를 기다리지 않는다. C3-06·C4-05 역시 방법별 작은 작업으로 쪼갠다. 전 장비 매뉴얼 수집 완료는 M1 선행조건이 아니다.

숫자·기준이 비어 있으면 현장 비교의 합격 판정은 하지 않는다. 동일 코드로 만든 기대값만으로 독립 계산을 검증하지 않는다. 시험 중 결과를 보고 허용차를 넓혔다면 사유·재검토를 남기고 최초 계획과 구분한다.

## H. 의뢰가 실제로 흘러가는 예

1. 직원이 신청서·제품 자료를 폴더에 넣는다. AI는 스마트폰/Wi-Fi와 의뢰 목적의 근거를 추출하고 신규 건으로 등록한다.
2. 시장·범위가 확인되면 방법을 선택한다. 출력 목표가 빠졌다면 영향 항목과 자료 요청을 만들고 이미 가능한 정리는 진행한다.
3. 보완 후 계획을 고정하고 실제 자산·교정·지원 능력과 일치하는 셋업 카드를 발행한다.
4. 직원이 시료 ID를 확인하고 카드대로 연결한다. AI는 완료 답변과 가능한 장비/경로/RF 관측을 함께 확인한다.
5. 현장 실행기가 잠금·전제를 검사하고 DUT 조건·측정·원본 취득을 수행한다. 상태 불명은 성공으로 처리하지 않는다.
6. 계산·판정·보고·리뷰를 수행한다. 유효한 부적합이면 그대로 기록하고, 무효이면 원인과 필요한 조치를 만든다.
7. 최초 출력 실증에서는 단일 항목 보고를 만든다. M2에서는 방사/AC 등 필요한 셋업 변경 요청 후 전체 적용 범위를 완료한다.
8. 완료 묶음과 남은 연관 평가·발행 상태를 전달한다. 운영 기록으로 개입 시간과 장애·재시험 원인을 평가한다.

## I. 다른 PC의 개발총괄에게 전달할 지시

```text
현재 독립 개발 복제본과 진행 작업을 보존하고,
codex/autolab-build-guide-20261028 브랜치를 fetch해서
AUTOLAB-BUILD-GUIDE.md와 docs/autolab-build/00-overview.md를 읽어 주세요.
현재 구현·검증 증거와 work-items.csv를 B00부터 대조하고,
이미 완료된 작업은 증거로 인수하고 부족한 작업만 배정하세요.
M1 전도 출력의 접수→실측→원본→성적서→리뷰를 우선 연결하세요.
수집1~8과 P01의 기존 역할·진행 자료는 유지하세요.
새 문서 파일은 현재 개발 브랜치의 통합 절차로 반영하고,
계획 문서의 존재를 구현·현장 검증 완료로 표시하지 마세요.
```

GitHub 게시만으로 다른 세션의 인수는 끝나지 않는다. 담당자는 실제 읽은 커밋·현재 작업 경로·대조 결과·첫 작업 ID를 인수 기록에 남긴다.
