# Vertex 접수 비교 등록 구현 계획

2026-10-25, Asia/Seoul. [고정 설계](../specs/2026-10-25-vertex-intake-comparison-design.md)의 기존3 수정 한 단위를 수행한다. 총괄이 정상 게시한 정확 base를 별도로 전달하고 개발3은 기존9c00 clone/branch/proof를 보존한 새 독립 clone/전용 branch에서 시작한다.

1. 현재 root와 담당 source·소유3·기존41 및 원 No/I1/I2를 확인한다. 원 raw inputpack004와 별도 wire005, literal1410·neutral producer·context C1 SHA를 대조한다. 원 모델 응답/독립 기대/Store는 열지 않는다.
2. 독립 수용 기대는 owner 새 core 작성 전에 봉인한다. 기존 connection과 3개 고정 접수 entry, cross-case·version·producer/schema/context 변조, transport 실패 시 decoder0과 한도/누적예산 경계를 포함한다. 해당 봉인은 owner가 읽지 않는다.
3. 담당은 신규 unit RED를 기록한 뒤 기존 core/test/usage만 수정한다. public API/DTO 키를 바꾸지 않고 명시 case 분기에서 genuine builder/decoder를 직접 사용한다. private descriptor11 외 새 실행 구조나 wrapper를 만들지 않는다.
4. strict와 semantic not_assessed·원 I1/I2·누적 예산·원 실패를 검증한다. 기존41과 새 관련 검사를 실행하고 source 소유 외 불변·문서 UTF-8/링크·diff를 확인한다. 실제 ADC/auth/모델/네트워크/장비는 담당 검증에서0이다.
5. 담당이 정확3의 정상 commit/push와 원격 SHA·GitLF/raw 핀·유계 evidence를 전달한다. 독립 검수/필요 수정 뒤 총괄이 정확 source를 인수해 genuine 의존성·관련 회귀를 확인하고 정상 commit/push·원격 대조한다.
6. 개발4의 등록 입력/업무 상태 화면은 기존 보호 UI 수용 뒤 별도 최소 소유로 배정한다. 등록과 실제 호출 승인을 구별하며 첫 connection ledger를 재사용/보존한다. 이번 패치에서 실제 업무 호출이나 예산 확대를 하지 않는다.

완료 조건은 3개 명시 C1 입력과 literal schema가 기존 decoder에 정확 연결되고 원 connection/실패·예산 경계가 유지되는 것이다. 실제 의미평가·Store admission·operator/계획/설명·실물 검증은 후속 단계이며 not_assessed/null을 완료로 바꾸지 않는다.
