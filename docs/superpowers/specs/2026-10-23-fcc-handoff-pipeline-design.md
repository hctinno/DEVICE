# FCC 자료 수집 의뢰와 공통 파이프라인 설계

사용자 요청: 필요한 규정·KDB·표준·시험방법·장비 문서의 전체 수집 목록과 링크를 다른 에이전트에 전달하고, 자료를 기다리는 동안 공통 파이프라인을 구축한다. 기존 보고서 양식보다 규격과 표준 시험방법을 기준으로 설계한다.

## 선택과 범위

기존 LIMS 연계, 공통 코어+어댑터, 모든 제어 소프트웨어 자체 개발을 기존 준비계획에서 비교했다. 현 단계는 기존 Python/SQLite 자산과 연결하는 공통 코어+어댑터를 구현한다. 이는 구현자의 선택이며, 사용자가 요청한 진행 범위 안의 되돌릴 수 있는 선택이다. 현재 work 브랜치와 전용 클라우드 작업공간을 계속 사용하고 기존 산출물을 보존한다.

규정 적용의 최종 확정, 모든 FCC 시험방법, 실장비 제어, 무인 현장 운전, 정식 성적서 발행·TCB 제출을 구현 완료로 주장하지 않는다. 이 기능은 검증된 규정 모듈·장비 연결·현장 자료가 있어야 활성화할 수 있다. 이번 결과는 자료 인수부터 제품·계획·실행 데이터·계산·초안 보고서까지 실행 가능한 공통 소프트웨어다.

## 수집 의뢰

FCC 범위표의 모든 규정군, 주요 KDB 목록의 후보 전부, 법규 편입 표준 및 시험방법의 관련 문서, 보고/인정/시설 지침, 개발 인터페이스 문서, DB의 모든 장비 모델과 식별 불완전 행을 대장으로 생성한다. 공식 최신 목록의 재탐색과 참조문서 재귀 수집을 별도 과제로 지정한다. 검색 색인 후보 목록을 현행 전체 목록으로 표현하지 않는다. 국가 확장 자료는 FCC 우선 완료 후 수집할 별도 목록이다.

링크 종류는 direct_file / official_page / official_portal / generated_search로 구별한다. 모르는 PDF 주소는 만들지 않는다. 장비 매뉴얼은 모델·세대·옵션·펌웨어별 적용성을 기록한다. 유료/로그인/열람 전용/폐기/대체/찾지 못함도 결과로 반환한다. 인증서·교정값·IP 주소 등 현장 고유 자료를 인터넷에서 대신 추정하지 않는다.

## 공통 소프트웨어

- Python 3.10+, SQLite, 기존 openpyxl. JSON Schema로 인수 문서 검증. MCP 공식 Python SDK로 stdio 도구 제공. HTML과 ReportLab A4 PDF는 초안만 생성한다.
- 수집 ZIP은 manifest.json을 갖는다. 파일 경로·중복·SHA256·크기·실제 PDF 헤더를 확인하고, 압축 해제 제한을 적용한다. 문서는 데이터이며 실행하지 않는다. 전체 검증 성공 후 DB에 원자적으로 등록한다.
- 등록은 동일 패키지 재요청에 멱등적이다. 기존 문서 ID의 다른 바이트를 덮어쓰지 않는다. 바이트를 내용 해시로 보관하고 인수 상태와 기술 검토 상태를 구별한다.
- 제품 정보, 시험계획, 방법 프로필, 실행 기록, 원시 파일, 결과, 감사 이벤트를 고정 ID로 연결한다. DB의 외래키와 입력 검증으로 다른 시험 건의 자료 혼합을 막는다.
- 적용 판단과 세부 시험 설정은 검토된 입력을 받는다. 미지원 범위·자료 부족은 blocked로 반환하고 추측한 합격값을 만들지 않는다.
- 계산은 유한 숫자·단위·입력 참조를 검사하는 결정적 코드로 수행한다. 1차 지원은 dB 보정 합산과 dBm→W 변환이다. 규정 한계값은 소스 ID가 연결된 방법 프로필에서 받으며 FCC 숫자를 임의 기본값으로 넣지 않는다.
- 실장비 제어 어댑터는 미연결을 명시적으로 반환한다. 데모는 합성 데이터로만 실행하고 모든 결과·보고서에 합성 상태가 이어진다.
- 문서나 방법이 미검토이면 계산값은 보존하되 규정 판정은 blocked다. 해당 판정과 공식 발행 권한은 별도이며 모든 보고서는 DRAFT다.
- CLI와 MCP는 같은 서비스 함수를 호출한다. 외부 전송·구매·실장비 쓰기는 이번 구현에 없다.

## 완료 기준

1. 수집 요청 ZIP을 다른 에이전트에게 전달할 수 있고 각 요청에 ID·범위·우선순위·링크·수집 조건이 있다.
2. 장비 모델 전체와 모델 미연결 행이 빠짐없이 의뢰에 포함된다.
3. 정상 수집 ZIP을 인수하고 재인수해도 중복되지 않는다. 잘못된 해시/경로/자료는 거절한다.
4. 합성 기준 사례가 제품→계획→실행→계산→추안 보고서로 끝까지 흐르며 문서 미검토 상태가 보고서에 유지된다.
5. 유효하지 않은 숫자·단위, 다른 시험 건의 자료, 중복 ID, 실행 실패를 적합 결과로 만들지 않는다.
6. 기술 검토·지원 범위·실측 검증의 미완료 항목이 상태 조회와 보고서에 보인다.
7. 의미 있는 단위/통합 테스트와 독립 코드 검토를 수행하고 사용 명령과 한계를 문서화한다.
