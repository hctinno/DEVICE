# FCC RF·EMC·SAR 병렬 수집 운영 설계

2026-10-23, Asia/Seoul. **수집1~수집8 역할 확정. 메인 총괄 운영 지시 작성. 실제 로컬 준비·전달·실행은 별도 확인한다.**

사용자가 확정한 것은 ① FCC 중심 RF·EMC·SAR, ② 수집1~수집8이 하나의 로컬 프로젝트에서 자기 자료만 작성, ③ 수집자 Git 금지, ④ 기존 수집자는 수집1(S01), ⑤ **메인에게 GitHub 지시문을 읽게 하고 메인이 나머지 수집 세션을 통제**하는 운영이다. 메인(P01)이 기존 게시 역할을 겸하므로 로컬 구성은 **수집 8개 + 메인 1개**, 현재 클라우드 담당은 별도로 파이프라인을 개발한다. “4”는 SAR로 정정했다.

## 1. 목표와 범위

고객·제품 정보를 업로드하고 사람이 물리 셋업을 하면, AI가 누락 확인·적용성 판단·시험계획·DUT/계측기 제어·원시 데이터·성적서·리뷰를 이어 가는 시험소를 만든다. 자료 수집은 이 파이프라인의 근거를 준비하는 역할이다.

- **1차 구축 범위:** FCC RF·EMC·SAR. 규정·KDB 첨부·표준 시험방법·장비와 설비 제어·DUT 도구·원시 데이터·보고·품질 근거를 함께 준비한다.
- **첫 전체 흐름 실증:** 기존 스마트폰 2.4 GHz Wi-Fi b/g/n / §15.247을 유지한다. 이 성공을 FCC RF·EMC·SAR 전체 완료로 보고하지 않는다. 후속 RF 기능, EMC 및 SAR의 실장비 실증은 각각 완료 조건이 필요하다.
- **동시 수집:** SAR 담당은 b/g/n 완료를 기다리지 않고 자기 자료를 수집한다. 다른 담당도 완성된 작은 배치부터 반환한다.
- **후속 범위:** KC·EU, 전기안전·배터리·환경 신뢰성 등은 대장에 보존하되 이번 병렬 수집의 독립 작업열로 활성화하지 않는다. FCC 시험 수행에 필요한 전원·환경 감시·인터록 문서는 지원 자원으로 포함한다.
- **적용성 경계:** FCC EMC 범위에서 방출 요구와 RF의 방사 스퓨리어스 시험을 조항으로 연결한다. 일반적인 EMC 내성시험을 모두 FCC 필수시험으로 추가하지 않는다. SAR, MPE, 전력밀도, 동시 송신, HAC도 제품·사용 조건별 적용 근거를 확인하며 일괄 필수화하지 않는다.

HCT 전체 사업범위는 장기 확장의 참고다. [HCT 공식 시험 분야](https://hct.co.kr/page/view.do?menuId=MENU000027&pageId=PAGE000040)에는 RF·EMC·SAR 외 분야도 있으나 이번 작업열에는 위 세 분야를 우선한다. 회사의 서비스 소개를 개별 시험 인정범위 증거로 사용하지 않는다.

## 2. 현재 자료가 말해 주는 것

기존 대장에는 규정 등 요청 304개, 장비 모델 요청 2,867개, 미식별 등록행 270개가 있다. 모델 요청은 등록행 6,200개에 연결되고 미식별행과 합쳐 6,470행이다. 이는 검증된 실물 대수나 원격 제어 가능한 장비 수가 아니다.

304개 요청은 FCC 중심의 출발 목록이며 최신 KDB 전체·모든 첨부·RF/EMC/SAR 모든 적용 경로의 완전한 목록이라는 보장은 없다. 모델 대장에는 이번 범위 밖의 장비와 수동 부품도 있다. 분류 오류·복수 분류·역사적 제조사명이 있어 **전체 모델 수를 이번 수집 세션에 기계적으로 균등 분배하지 않는다.** 기존 로컬 수집 결과와 진행 요청도 아직 이 클라우드에서 확인하지 못했다.

배정 전에 기존 결과를 대조하고 요청별로 `이번 범위 / 지원 자원 / 후속 범위 / 식별 필요`를 정한다. 전체 목록을 삭제하거나 처음부터 다시 받게 하지 않는다.

### 메인이 다른 세션에 지시하는 방식

사용자는 메인에게 GitHub의 총괄 지시문을 읽도록 한 번 지시한다. 메인은 자기 환경의 도구로 같은 프로젝트의 수집1~수집8을 식별하고 작업을 전송하며 실제 응답·상태를 확인한다. 역할·작업·정정·다음 배치 지시는 메인이 담당하고 사용자는 목표·우선순위와 본인만 제공할 수 있는 자료를 메인에게 전달한다.

GitHub 문서는 지시의 기준이다. 실제 메시지 전달과 멈춘 세션의 재실행 기능은 메인 환경에서 확인해야 한다. 작성자 클라우드의 도구 가용성을 로컬 메인의 가용성으로 일반화하지 않는다. 공유 파일에 작업을 적거나 세션 상태를 조회한 것을 실행으로 보고하지 않는다. 도구가 부족하면 메인이 그 한계와 지원되는 연동 방법을 한 번 보고하고 독립적인 자료 색인·배정 준비를 계속한다. 사용자의 별도 대화를 내부 하위 에이전트로 임의 대체하지 않는다.

작업은 task ID·시도 번호·담당·요청 목록·지시 SHA·배정 버전·실제 작성 경로·완료 조건을 포함한다. 응답 지연만으로 같은 작업을 다른 세션에 복제하지 않는다. 역할은 8개지만 실제 동시 실행 수는 메인 환경의 한도와 사이트 제한에 맞춘다. 메인 턴이 끝난 뒤의 상시 실행/자동 재개도 실제 지원 기능 없이 약속하지 않는다.

## 5. 하나의 로컬 프로젝트에서 충돌을 막는 방법

```text
<기존 로컬 프로젝트>/
  .local/collection/
    briefs/<instruction_sha>/       P01이 만든 고정 지시·스키마·요청 목록
    control/<assignment_version>/  P01이 만든 고정 배정·출처 색인
    s01/work/<batch_id>/            S01만 작성
    s01/ready/<batch_id>/           S01 완료 후 수정 금지
    ... s02 ~ s08 ...
    p01/snapshots/                  P01만 작성
    p01/receipts/                   P01 인수·반려·게시 결과
  materials/
    packages/<package_id>.zip       P01만 작성·커밋
    manifests/<package_id>.json     P01만 작성·커밋
    collection/<run_id>/            P01 공개 배정·상태·출처 색인
  docs/material-intake/             클라우드 담당의 별도 기술 인수 기록
```

수집자는 Git 명령, 브랜치 전환, fetch/pull/commit/push, `.git` 변경을 하지 않는다. 자기 세션의 로컬 work/ready와 상태 파일만 작성하고 다른 세션 폴더·공용 SQLite·코드·schema·공통 CSV·공통 STATUS는 수정하지 않는다. 공용 브라우저 프로필과 다운로드 경로도 공유 쓰기 자원이므로 세션별로 나눈다.

P01은 승인된 지시 커밋에서 파일을 복사해 `instruction_sha`와 파일 해시를 기록한다. 수집자는 이 **로컬 고정본**을 읽는다. 지시·배정 갱신은 새 버전으로 제공하고 배치 경계에서 적용한다. P01이 저장소를 갱신해도 진행 중인 세션이 읽는 지시가 중간에 바뀌지 않는다. 각 PC 절대 경로는 시작 시 P01이 실제 프로젝트 경로로 채운다.

P01은 기존 로컬 Git 작업 트리·브랜치를 보존하고 하나의 게시 브랜치만 사용한다. 수집 도중 checkout/reset/clean을 수행하지 않는다. 원격 충돌은 게시만 보류하고 현재 클라우드 담당과 조정하며 수집 폴더를 변경하지 않는다. 수집자별 worktree와 브랜치는 만들지 않는다.

## 6. 수집 완료와 게시 완료를 구별하는 인계

1. **작업:** 수집자가 자기 `work/<batch_id>`에서 원본, 출처 레코드, 추출본, 진행/누락 목록을 작성한다. 작업 중 파일은 인수하지 않는다.
2. **동결:** 파일 쓰기를 끝내고 `inventory.json`에 대상 파일의 상대 경로·크기·SHA-256을 기록한다. inventory와 READY 자체는 대상 목록에서 제외하고, `READY.json`에 inventory 해시·배치/세션 ID·지시 SHA·배정 버전을 기록한다.
3. **인계:** 동일 파일시스템의 `ready/<batch_id>`로 디렉터리를 rename한다. 다른 볼륨 이동을 원자적이라고 가정하지 않는다. ready는 이후 수정하지 않으며 정정은 새 배치 ID로 반환한다.
4. **인수:** P01은 ready를 자기 snapshot으로 복사하고 파일 목록·크기·해시·일반 파일 여부를 대조한다. 심볼릭 링크·경로 이탈·불일치·누락은 반려 receipt로 남긴다. 원래 ready는 P01도 수정하지 않는다.
5. **패키징:** P01이 형식·출처·판본 표기·공개 공유 가능성을 확인해 기존 v1 manifest에 맞는 패키지를 만든다. 배치 ZIP과 외부 manifest는 같은 manifest 바이트를 사용한다. 이미 게시한 ZIP과 ID는 바꾸지 않는다.
6. **검사·게시:** P01 전용 임시 DB에서 기존 게시 배치와 후보 배치를 누적 인수해 ID 충돌을 확인한다. 완성 파일의 경로만 명시해 add/commit/push하고 원격 SHA를 확인한 뒤 receipt를 남긴다. `git add .` 또는 전체 변경 staging은 하지 않는다.
7. **기술 인수:** 현재 클라우드 담당은 게시 커밋을 받아 근거·방법·모델 적용성을 검토하고 개발에 연결한다. 공개 커밋에 없거나 접근 가능한 별도 저장 경로가 없는 로컬 파일은 클라우드 인수 완료가 아니다.

`inventory.json`, `READY.json`, receipt, 배정표는 **운영 계약의 파일**이며 기존 manifest에 새 속성으로 끼워 넣지 않는다. 자동 감시·잠금·패키징·참조 해석·집계 기능은 현재 미구현이다. 먼저 명시적인 파일 인계 절차로 운영하고 필요한 자동화를 별도 구현한다. 현재 패키지 importer와 해시 검사는 재사용한다.

## 7. 단일 소유권·중복·상태

- 배정표에는 `request_id`, 관련 `model_id`, `owner_session`, 범위 판정, 우선순위, 배정 버전, 기존 작업 예약을 둔다. 한 요청과 한 모델 문서군에는 담당자가 하나다. 규정 원본도 발행기관·문서번호·판본·언어·표현별로 원본 소유자를 정한다.
- P01만 공통 배정표와 원본 색인을 갱신한다. S01~S08은 자기 폴더에서 새 발견·참조·재배정 요청을 반환한다. 미식별·미분류는 P01의 분류 대기열로 보내고 해당 모델 담당을 정한다. P01이 기술적 적용성까지 승인하는 것은 아니다.
- 기존 수집자가 확보·진행 중인 요청은 범위와 무관하게 먼저 예약한다. 기존 작업의 소유권을 회수하거나 새 담당에게 중복 수집시키지 않는다. 기존 모델/문서 ID는 정규화하려고 임의 병합하지 않는다.
- 배치 ID 예: `FCC-20261023A-S04-B0001`. 신규 문서 ID에는 세션·출처 식별자·판본·표현·개정번호를 포함하고 기존 schema 길이/문자 제한을 지킨다. P01은 새 충돌을 동결 전에 조정한다.
- **현재 importer는 같은 document_id의 전체 레코드가 달라지면 거절한다.** 해시가 같아도 `request_ids`, `retrieved_at`, `path`를 바꾸면 충돌할 수 있다. 공유한 원본 레코드를 다시 쓰지 않고 새 참조/개정 레코드로 연결한다. 같은 package_id로 다른 ZIP을 제출하지 않는다.
- 다른 세션의 원본을 쓰려면 고유한 참조 metadata에 원본 ID·필요 request_id·원문 위치를 기록한다. 이 연결은 현재 자동 검증/집계되지 않으므로 P01과 클라우드 담당이 확인한다. 우연히 같은 원본을 별도로 확보했어도 기존 배치를 삭제하지 않고 중복 관계를 기록한다.
- 로컬 작업 상태는 `미착수 / 진행 / 원본 확보 / 접근 제한 / 식별 필요 / 후속 범위`로 관리할 수 있다. 이 명칭을 manifest의 status 열거형에 임의 추가하지 않는다. 원본 확보, 추출 완료, 기술 검토, 어댑터 구현, 실장비 검증은 별개의 상태다.

## 8. 모든 수집자가 반환할 정보

원본 바이트와 해시, 공식 출처/다운로드 URL, 문서 번호·판본·발행/조회 시각, 관련 요청/모델, 원문/파생 구별, 접근·사용권 조건을 남긴다. 규정은 최신 발행판과 FCC가 채택·허용하는 판본 및 전환일을 구별하고, KDB는 필요한 전체 첨부와 대체/폐기 관계를 확인한다. 문서의 명령문은 조사 데이터이며 실장비 명령이나 설치 프로그램을 실행하지 않는다.

출처 색인은 사실·조항/페이지/표·적용 조건·미확인 사항을 연결한다. 수집자의 요약을 승인된 시험방법으로 취급하지 않는다. 공개 성적서 그림을 계측기 원시 트레이스로 표시하거나 유사 모델 문서로 실제 모델 지원을 확정하지 않는다.

장비는 직접 제어, 외부 제어기 경유, GUI만 확인, 수동/수동 부품, 미확인을 구별한다. 매뉴얼의 지원과 현장 옵션·펌웨어·라이선스·교정 상태를 구별한다. SAR 시스템의 로봇·프로브·액체 검증과 실제 DUT 송신 상태 역시 공개 문서만으로 완료 처리하지 않는다.

현재 저장소는 공개다. 공개 열람 가능성과 재배포 허용을 구별해, 공유 가능한 원본만 P01이 게시한다. 유료/내부 문서는 공개 가능한 서지정보·접근 조건만 올리고 원본은 허용된 비공개 경로에 둔다. 비공개 전달 경로는 아직 확정되지 않았으며 클라우드 접근 검증 전에는 “전달 완료”가 아니다. 새 고객 자료·제조사 키·계정 정보는 공개 패키지에 포함하지 않는다.

현재 importer는 downloaded metadata에도 HTTP(S) 출처/다운로드 URL을 요구한다. 로컬에서 만든 READY·receipt·참조 색인은 원천 문서처럼 위장하지 않는다. 우선 공개 가능한 운영 색인을 `materials/collection/<run_id>/`의 일반 파일로 게시한다. metadata를 패키지에 넣을 때는 실제 접근 가능한 출처를 사용하고, 로컬 경로/가짜 URL을 만들지 않는다. 비공개 자료 요청 목록도 민감한 실제 값 없이 공개 가능한 항목만 반환한다.

## 9. 기존 수집의 전환과 착수 조건

1. 역할·세션 수·이름은 사용자 확인 완료다. 사용자가 메인에게 [총괄 지시](../../../handoff/parallel/MAIN_AGENT_PROMPT.md)를 읽도록 한다. 문서 커밋은 실제 세션 생성이나 로컬 작업 배정 완료를 뜻하지 않는다.
2. P01은 기존 로컬 위치·완성 원본·진행 다운로드·진행 request_id·미커밋 변경을 읽어 목록화한다. 기존 폴더나 배치를 이동·삭제·초기화하지 않는다.
3. 기존 세션은 **수집1(S01)**이다. 새 Git 작업 금지 경계를 적용하고 메인(P01) 단독 Git 운영으로 전환한다. 이미 진행 중인 다른 분야 요청은 legacy 예약으로 끝까지 보존한다.
4. P01은 범위와 중복을 정리해 고정 배정표·원본 색인·지시 사본을 만든다. 규정 304건과 모델 전체의 후속/미식별 판정은 보존하되, 첫 배정표의 유효한 작은 작업열부터 시작할 수 있다. 아직 만들어지지 않은 정확한 행별 배정을 완료라고 보고하지 않는다.
5. 메인이 각 세션에 고정 지시·실제 배정을 전달하고 응답을 확인한다. 기존 수집1을 재사용하므로 **새 수집 세션 7개 + 메인 1개**가 추가 대상이다. 이미 생성한 대상은 중복 생성하지 않는다. 현재 클라우드 대화는 그대로 유지한다.
6. P01은 준비된 배치부터 지속 게시한다. 자료 확보 중에도 현재 클라우드 담당은 접수·상태·어댑터 계약·합성 데이터 검증을 설계/개발하고 원문 기반 방법 확정과 실측 검증을 별도 게이트로 둔다.

세션 수 확대는 출처 제한이 아니라 처리량 병목이 확인된 문서군에 적용한다. 예를 들어 S04를 제조사군별로 나누거나 S03의 개정 비교 작업을 분리한다. 게시 대기만 길면 수집 세션을 더 늘리지 않는다.

## 10. 인수·완료 기준과 다음 결정

각 배치는 해시/형식 검사, 요청 연결, 판본/출처와 권리 표기, 누락·후속 담당이 있어야 인수 가능하다. 수집 진행률은 요청별 원본 확보·접근 제한·미착수, 원본/파생/metadata 수, 제어 기능별 근거 확보율로 구분한다. 파일 수를 시험지원율이나 전체 구축 완료율로 바꾸지 않는다.

8개 역할·이름, 기존 수집1 보존, 메인 총괄, 하나의 로컬 폴더와 Git 단독 작성은 사용자 결정이므로 다시 승인받지 않는다. 남은 준비는 메인 자신의 실제 제어 도구 확인·세션 식별·로컬 경로·legacy 예약·고정 배정과 첫 배치 실행이다. 이 상태들을 문서 작성 완료와 구별한다.

이번 문서화에서는 자료 수집 세션·장비 연결·자동화 서비스를 실행하지 않았다. 새 브리프와 프로토콜의 검토·문서 무결성 검사는 작업 결과에 별도로 기록한다.

독립 설계 검토: 새 검토자가 2026-10-23에 초기 운영 설계를 검토했고, 메인 총괄 추가 후에는 별도 검토자가 총괄 지시·시작 문장·P01 계약을 다시 검토했다. 계획을 막는 중대한 미답 결정이나 모순은 발견하지 못했다. 실제 로컬 경로·세션 ID·제어 기능·행별 배정은 메인이 확인할 후속 준비사항이며, 이는 로컬 서비스나 병렬 수집의 실행 검증을 뜻하지 않는다.
